Findings report · for New Measure

TriggerDevBench

A reliability benchmark for Trigger.dev's self-hosted platform, built in the task-directory format of New Measure & Atomicwork's ITSMBench, adapted to score a platform's own behavior against its claimed guarantees instead of an agent's judgment.

Target: Trigger.dev v4.5.16, self-hosted (Docker) Tasks: 10 built, all live-verified Method: black-box, real infrastructure, no mocks

Executive summary

Every task in this report was run against a real self-hosted deployment on real hardware — no simulated responses. Three findings are confirmed platform bugs; one is a confirmed pass at the platform's own claimed SLA; the rest establish that the core correctness guarantees (idempotency, retries, replay, queue fairness) hold under adversarial, concurrent conditions.

The ten tasks

Numbered in discovery order — each task's id (task-01 … task-10) matches its directory in the repo, so the order below is also the literal file order.

01
Trigger a task id no worker will ever register
Deploy-drift: a typo'd or renamed task identifier, permanently unfulfillable.
Run stayed PENDING_VERSION at T+11:02, past its own 10-minute TTL. Trigger call itself returned HTTP 200 — a false-positive success.
Fail
02
Cancel mid-execution — does cleanup code ever run?
5 independent trials, canceled 2s into a 10s task, checked for cooperative signal.aborted output.
5/5 trials: status: CANCELED. 0/5 trials showed any output — confirmed deterministic hard-kill, not a race.
Fail
03
Webhook burst from a sender with no retry logic
200 individual triggers, fired as fast as possible, against the 750 req/window default limit.
Load-dependent: 0/200 lost in isolation, 173/200 (86.5%) lost when run alongside other concurrent traffic on the same instance.
Disclosed
04
Real SIGKILL of the worker mid-execution
Killed the entire dev-server process tree 7s into a 30s task. Never restarted it.
Resolved to CANCELED / TASK_RUN_STALLED_EXECUTING at 300.06s — within 57ms of the platform's own 300.00s claimed SLA.
Pass
05
Self-hosted's missing checkpoint support, measured
4× wait.for(20s) on a concurrencyLimit: 2 queue.
Batch took 41.4s — matching the blocking model (2×20s), not the non-blocking one. Confirms docs: self-hosted Docker has no CRIU checkpoint support at all.
Disclosed
06
Idempotency key under a true concurrent race
5 simultaneous triggers, same idempotencyKey, no delay between calls.
Collapsed to 1 run, 1 execution — enforced via a Postgres unique constraint, not app-level locking.
Pass
07
Exponential backoff, wall-clock verified
3 forced failures, then success — checked real delay, not just retry count.
attemptCount: 4, wall time 10.8s against a 7.0s theoretical minimum backoff.
Pass
08
Wildcard concurrency key vs. queue fairness
Regression check on a previously-fixed starvation bug (concurrencyKey: "*").
3 distinct-key runs completed in 1.36s while the wildcard-key run held for 6s — no starvation.
Pass
09
Replay determinism
POST /replay on a pure task — new run, or a silent cache hit?
New run id, executionNumber: 2 (genuine re-execution), identical output hash to the original.
Pass
10
4MB oversized payload
Adversarial input size — looking for a hang, crash, or silent truncation.
Clean HTTP 413, "Request body too large". No hang, no truncation.
Pass

Grounding & methodology

Every finding was cross-referenced against the Trigger.dev source (cloned locally, not read from docs alone) before being written up, and the eval design draws directly from published methodology rather than ad hoc poking.

Source cross-reference

pendingVersion.test.ts

448 lines, 3 scenarios — all require a matching worker to eventually arrive. Never tests the "no worker ever will" case task-01 reproduces.

Source cross-reference

cancelling.test.ts

450 lines — zero assertions on output or cleanup behavior for a canceled run. Task-02's finding isn't covered by the platform's own tests either.

Source cross-reference

snapshotStoreChaos.test.ts

Trigger.dev's own white-box chaos suite — in-process fault injection at 3 named write boundaries, validated against a TLA+ model. Task-04 is this suite's black-box counterpart: a real SIGKILL, not an injected exception.

Source cross-reference

docs/self-hosting/docker.mdx

"No checkpoint support… only ever experimental when self-hosting." Confirmed zero references to "checkpoint" anywhere in packages/cli-v3/src/. Task-05 measures the operational consequence.

Methodology

Jepsen

Adversarial workload + fault injection, scored against a system's claimed guarantee rather than general correctness. Task-06's concurrent-race design follows this directly.

Methodology

"Simple Testing Can Prevent Most Critical Failures" (OSDI '14)

92% of catastrophic distributed-systems failures trace to mishandled non-fatal errors. Every bug found here — task-01, task-02, task-03 — is exactly this class: an error-handling path, not a deep distributed-systems fault.

Methodology

"Beyond pass@1" (2026)

A single crash/cancel/race trial can't distinguish deterministic behavior from a timing-dependent coin flip. Task-02 runs 5 independent trials and reports a rate, not one boolean.

Methodology

SWE-bench

Build the eval directly from a real-world artifact (a GitHub issue, a source-code gap) rather than an invented scenario. Every task here traces to a cited commit, doc, or test file.

Why this looks like ITSMBench

Every task keeps ITSMBench's directory shape and reward.txt scoring convention. The one deliberate departure: ITSMBench scores an LLM agent's judgment inside environment's main container; this benchmark scores the platform itself, so each task's driver/ is a fixed, deterministic script standing in for the agent — doing exactly what instruction.md describes, no model or harness selection involved.

tasks/task-01-pending-version-stuck-run/ task.toml schema, timeouts, docker image ref instruction.md ticket-style prompt README.md narrative: expected vs. found, why it matters environment/ shared self-hosted Trigger.dev stack driver/ deterministic action (replaces the agent) tests/ test_outputs.mjs + test.sh -> reward.txt

What this makes possible next

  1. Scale to the full candidate list. 10 of 50+ scoped long-running and adversarial scenarios are built — checkpointed multi-day waits, deploy-mid-flight, cross-node causal consistency, sustained-backlog fairness at scale.
  2. Repeat-trial scoring throughout. Extend the task-02 reliability-science pattern (N independent trials, a rate not a boolean) to every timing-sensitive task in the suite.
  3. Port the format to other durable-execution platforms. The driver/tests split is platform-agnostic — Temporal, AWS Step Functions, and Inngest are direct next targets using the same shared-environment pattern.
